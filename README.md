# AI Codebase Assistant

Chat with a real GitHub repository and get answers grounded in the actual source code, with citations to specific files and line numbers.

## Status: Milestone 1, Day 5 — Chat / Retrieval (complete)

### What's implemented

- **Auth, repo import, parsing, chunking, embeddings** — Days 1-4.
- **Chat, end to end:** start a chat scoped to a `ready` repository → ask a question → the question is embedded → `$vectorSearch` retrieves the top-K most relevant chunks, filtered to that repository → a system prompt is built instructing the model to answer only from that context and cite `[filepath:startLine-endLine]` inline → **Groq (Llama 3.3 70B)** streams the answer token-by-token over Server-Sent Events → citations are parsed out of the completed response and stored alongside the message.

### LLM provider: why Groq, not Claude

The Anthropic API requires a funded account - a `$0` credit balance returns a `400` on every request (confirmed live during development). Groq's free tier needs no payment method at all, which is the same reasoning that led to running embeddings locally on Day 3-4: an external account that can block the whole pipeline isn't acceptable for a project meant to just work. `IChatCompletionProvider` was built specifically to make this swap cheap - one new client file (`clients/groq-chat.client.ts`), one line changed in the composition root, nothing else touched.

Worth being upfront about the trade-off: Llama 3.3 70B (an open model) can be less reliable at strictly following the "always cite in this exact format" system prompt instruction than Claude would be. If citation quality looks inconsistent in testing, that's this trade-off surfacing, not a bug in the prompt or the citation-extraction regex.

### One manual setup step this milestone genuinely requires: the Atlas Vector Search index

`$vectorSearch` cannot be created through Mongoose or any code in this repo — it's configured directly in the Atlas UI (or via the Atlas Admin API), separate from normal MongoDB indexes. **Chat will not work until you create this.**

1. In MongoDB Atlas, go to your cluster → **Search & Vector Search** tab → **Create Search Index**.
2. Choose **JSON Editor**, select the `chunks` collection in your database.
3. Name the index exactly `chunk_vector_index` (must match `VECTOR_INDEX_NAME` in `src/repositories/chunk.repository.ts`).
4. Paste this index definition:

```json
{
  "fields": [
    {
      "type": "vector",
      "path": "embedding",
      "numDimensions": 384,
      "similarity": "cosine"
    },
    {
      "type": "filter",
      "path": "repositoryId"
    }
  ]
}
```

`numDimensions: 384` matches `all-MiniLM-L6-v2`'s output size exactly - if you ever change `LOCAL_EMBEDDING_MODEL` to a model with a different embedding dimension, this index has to be rebuilt to match. The `filter` field on `repositoryId` is what makes `$vectorSearch` correctly scope results to one repository instead of searching across everyone's imported repos.

5. Wait for the index status to show **Active** (usually under a minute) before testing chat.

### Architecture (additions since Day 3-4)

```
models/chat.model.ts, message.model.ts   chat + message schemas, with citation storage
repositories/chat.repository.ts           chat/message data access
services/retrieval.service.ts             embeds the query, runs vector search scoped to the repo
services/chat-prompt.ts                   pure functions: system prompt construction + citation extraction
services/chat-orchestration.service.ts    ties retrieval + prompt + streaming + storage together
clients/chat-completion-provider.ts       shared streaming LLM interface
clients/groq-chat.client.ts               Groq API streaming implementation (Llama 3.3 70B, free tier)
routes/chat.routes.ts                     POST /api/chats/:id/messages (SSE)
config/composition-root.ts                single source of truth for shared singletons (see below)
```

**Why a composition root now, when earlier days didn't need one:** `LocalEmbeddingClient` lazily loads a ~90MB model into memory on first use. Both indexing (`RepositoryImportService`) and chat (`RetrievalService`) need an embedding provider - if each route file built its own instance (as `repository.routes.ts` originally did), the model would load twice, doubling memory and load time for no reason. `config/composition-root.ts` builds every shared dependency exactly once; every route file imports from there instead of constructing its own copies.

**A testing limitation worth being upfront about:** `$vectorSearch` only works on real Atlas - `mongodb-memory-server` (what the test suite uses) doesn't support it at all. `RetrievalService` and `ChatOrchestrationService` are fully unit-tested against fake repositories/providers (verifying retrieval scoping, prompt construction, citation extraction, streaming order, and message persistence), but the actual `$vectorSearch` query can only be verified live, against real Atlas, with the index above in place.

## Milestone 2 — GitHub OAuth, Private Repositories, Repository Management (complete)

Full design in `docs/milestone-2-design.md`, revised after a self-critical Principal Engineer design review (`docs/milestone-2-design-review.md`) that found real gaps — a genuine concurrency bug in OAuth state handling, an incomplete encryption design — before any implementation began, not after.

- [x] **Task 1 — `TokenEncryptor`.** A generic, reusable AES-256-GCM encryption service (`src/utils/token-encryptor.ts`) — deliberately not GitHub- or OAuth-specific, since "reversibly encrypt a sensitive string" is the same actual requirement whether the secret is a GitHub token today or some other credential this app needs to store later. Every real gap the design review found in the original encryption design is fixed here: a fresh, verified-unique IV per encryption (`crypto.randomBytes(12)`, confirmed via a standalone script against Node's real `crypto` module before writing the class, not assumed from documentation), the GCM auth tag stored and verified explicitly (tamper detection actually works, confirmed by test, not just claimed), a precise key format (base64-encoded 32-byte value, same generation pattern as `JWT_SECRET`), and a `keyVersion` stamped on every encrypted value so a future key rotation is additive rather than a breaking migration — without building full multi-key rotation machinery today, which would solve a problem that doesn't exist yet with only one key in use. A version mismatch throws a specific, actionable error rather than a generic, indistinguishable-from-tampering crypto failure. **A real bug caught by self-review before shipping**: the new `TOKEN_ENCRYPTION_KEY` env var was initially written as *required* — which would have immediately broken local dev, the entire test suite, and the already-working live Render deployment the moment this shipped, since nothing yet consumes it (the composition root isn't touched until a later task). Fixed to optional now, strictly validated only when present, becoming required once `GitHubConnection` actually depends on it. 14 new tests, including verifying that two encryptions of the identical plaintext produce different IVs and ciphertext (the specific property that makes GCM safe at all), and that tampering with either the ciphertext or the auth tag is detected, not silently accepted.
- [x] **Task 2 — `GitHubConnection` + `GitHubOAuthState` models and repositories.** Both new models, per the reviewed design. `GitHubConnection` stores `TokenEncryptor`'s `EncryptedValue` shape directly (`encryptedToken`, `iv`, `authTag`, `keyVersion` as separate fields — no reshaping needed between what the encryptor produces and what gets stored), with `upsert` (not `create`) semantics — the design review's specific fix for reconnection not hitting a duplicate-key error. `GitHubOAuthState` uses the same TTL-index pattern as `RefreshToken` (Milestone 1.5), and its repository's `consumeByState` method wraps a single atomic `findOneAndDelete` — the other concrete fix the design review required, verified with a dedicated regression test that fires two concurrent `consumeByState` calls against the same state and asserts exactly one succeeds. Both new models were added to the startup index-readiness wait in `config/db.ts` and `tests/setup.ts` — a checklist item every new indexed model gets checked against now, since it was missed once already for `ChatModel`/`MessageModel` back in Milestone 1.5. **A real implementation detail caught during self-review, not left ambiguous**: `GitHubConnection`'s upsert originally passed a plain object (no `$set`) to `findOneAndUpdate` — MongoDB's exact behavior for an update document with no operators is version-dependent territory not worth relying on implicitly, even though every field happened to be set anyway in this specific case. Rewritten to use an explicit `$set`, unambiguous regardless of driver version.
- [x] **Task 3 — The OAuth flow itself (connect, callback, disconnect).** `GET /api/auth/github` (rate-limited, per the design review) redirects to GitHub's authorize page; `GET /api/auth/github/callback` (no JWT possible here — GitHub's redirect carries none — identity is recovered entirely from the consumed `state` record) exchanges the code, fetches the GitHub user, encrypts the token, and stores the connection; `DELETE /api/auth/github` decrypts the stored token, attempts remote revocation, and deletes the local connection regardless of whether that remote call succeeds — a deliberate choice: the user's actual goal (stop this app holding their token) is achieved by deleting our own copy, and shouldn't be blocked by GitHub's API happening to be unreachable at that moment. Every GitHub endpoint shape (the token exchange's required `Accept: application/json` header — GitHub silently returns form-encoded data without it rather than erroring, a well-documented real gotcha; the `/user` endpoint's `Bearer` auth header; the revoke endpoint's exact path and Basic-auth requirement) was checked against GitHub's current docs before writing the client, not assumed. A real, easy-to-miss failure mode caught and specifically tested: GitHub's token exchange returns **HTTP 200** even for a failed exchange (expired code, mismatched redirect URI), with the failure only visible via an `error` field in the response body — checking `response.ok` alone would silently treat this as success. The callback route is the one deliberate exception to this API being pure JSON everywhere else: a human's real browser lands there directly after approving or declining on GitHub's own page, so it renders minimal HTML instead. **A real XSS-shaped gap caught during self-review**: the connected GitHub username was initially interpolated into that HTML with no escaping — low risk in practice (GitHub's own username rules make injecting HTML through a legitimate username effectively impossible), but relying on an upstream service's validation rules as the *only* defense against writing into HTML isn't a habit worth keeping, so explicit escaping was added regardless. 21 new tests across the client (mocking `fetch` to verify real request headers and the 200-with-error-body gotcha specifically) and the service (every path: successful connect, retry-then-succeed, state rejection, revoke-fails-but-disconnect-still-succeeds).

**⚠️ Requires real setup before this can be tested live** — unlike every previous task, this one needs an actual GitHub OAuth App:
1. GitHub → Settings → Developer settings → OAuth Apps → New OAuth App.
2. Set the **Authorization callback URL** to exactly match your `GITHUB_OAUTH_REDIRECT_URI` (e.g., `http://localhost:4000/api/auth/github/callback` for local dev) — GitHub rejects the callback outright if these don't match exactly.
3. Copy the generated Client ID and Client Secret into `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET`.
4. Generate `TOKEN_ENCRYPTION_KEY` with `openssl rand -base64 32` if you haven't already.

- [x] **Task 4 — Enable private repos in the existing import pipeline.** `GitHubClient.fetchRepoInfo()` now accepts an optional per-user token — when present, private repos are allowed through, and if the token doesn't actually grant access to that specific repo, GitHub's own API returns 404, already handled correctly by existing error handling with zero new authorization logic needed. `GitClonerClient.clone()` embeds the token into the clone URL for private repos. `RepositoryImportService` resolves which token to use entirely from the authenticated caller's own `ownerId` — the design review's explicit identity-resolution rule, actually implemented as the only possible code path rather than just documented as a principle. **A real, serious credential leak found and fixed, exactly the value of writing a test against a real failure rather than assuming a fix was sufficient**: the original fix kept the authenticated clone URL out of the log line directly, but a dedicated test — a real (deliberately failing) clone attempt with a fake token — caught that `simple-git`'s own thrown `GitError` embeds the *entire command line*, authenticated URL included, in a `task.commands` property. Logging `{ err, cloneUrl }` serialized that whole object, leaking the token anyway — and since the error propagates up to `RepositoryImportService.failImport()`, which logs it *again*, fixing only the original call site would have left a second leak untouched. The real fix: `GitClonerClient` now extracts only a sanitized message (defensively scrubbing any credential-shaped URL pattern too, in case a different git failure ever echoes one directly) and throws a clean `Error`, so the sensitive raw error object never propagates beyond one `catch` block — no code downstream, however carelessly it logs, can leak it. 15 new tests, including two files that previously had no coverage at all (`GitHubClient`, `GitClonerClient`), the latter using a real network call against a deliberately nonexistent repository rather than mocking `simple-git`'s internals, since mocking would only have proven the test's own assumptions about the library's behavior, not the real thing — which is exactly what caught the actual bug.
- [x] **Task 5 — Repository management endpoints (list, delete).** `GET /api/repositories` (a genuine, previously-missing basic CRUD gap, flagged both in the original design doc and the earlier production audit) lists the authenticated user's own repositories, sorted newest-first — reusing an index (`{ownerId: 1, createdAt: -1}`) that already existed, needing no new one. `DELETE /api/repositories/:id` cascades cleanup to every collection that actually references `repositoryId` — Chunks, Jobs, Chats, and Messages — not just Chunks, the only one the design review explicitly named; the same orphaned-data correctness requirement applies to all four, and this is a deliberate, stated extension of the literal design scope, not a silent one. Deletes run in dependent-data-first order (messages → chats → jobs → chunks → the repository document itself) without a database transaction — a stated trade-off: a real transaction would be the more complete answer, but for a portfolio-scale project, ordering the deletes this way costs nothing extra and meaningfully narrows the failure mode of a mid-delete crash, without taking on this project's first database transaction to do it. `RepositoryManagementService` is deliberately a new, separate class from `RepositoryImportService` — "how a repo gets imported" and "how a repo gets listed and removed" are genuinely different concerns. While extending `repository.routes.ts`, the ownership-check pattern duplicated across three separate handlers (flagged as a DRY opportunity by the Milestone 1.5 audit, never fixed at the time) was finally extracted into one shared `getOwnedRepositoryOrThrow` helper. This task's type-checking also caught a recurring issue worth naming honestly: the sandbox's aggregated project-wide `tsc` check gave a **false negative** twice in this task alone (reporting clean when four existing test files' fake repository implementations were genuinely missing newly-required interface methods) — caught only by checking each test file individually. Every fake across three pre-existing test files was updated to implement the five new repository methods this task added. 7 new tests for `RepositoryManagementService` specifically, including verifying the cascade actually reaches messages (not just chats), and that deleting one repository never touches another's data.

## Milestone 1.75 — Observability (complete)

Design decision, stated up front: this milestone does not introduce a dedicated metrics backend (Prometheus, a SaaS APM, etc.). Every question the roadmap asks ("how long does indexing take," "which stage is the bottleneck," "how many chunks were created") is answerable by adding precise duration and count fields to the structured logs (`pino`, JSON output) this project already has, queryable directly in Render's log viewer or any future log aggregator — solving the same problem a metrics system would, without adding a new service to run and a new thing that can itself break, for a project not yet at the scale where that trade-off pays for itself.

- [x] **Task 1 — Import pipeline timing.** Every stage of `RepositoryImportService`'s pipeline (clone, file walk, chunking, embedding, DB storage) now logs its own `durationMs`, plus a single `"Import complete"` summary line with total duration and a per-stage breakdown — directly answering "how long does indexing take" and "which stage is the bottleneck" from one log line, without needing to manually reconstruct timings from separate entries. Used `perf_hooks`' `performance.now()` rather than `Date.now()` for these measurements specifically because it's monotonic (immune to system clock adjustments), the technically correct choice for measuring durations rather than wall-clock time. A real, pre-existing gap was found and fixed while writing this: `RepositoryImportService` — the most complex orchestration class in the codebase — had **zero unit test coverage**, because three of its dependencies (`GitHubClient`, `GitClonerClient`, `ChunkingService`) were typed as concrete classes rather than interfaces, breaking this project's own established "depend on abstractions" pattern used everywhere else. Introduced `IGitHubClient`, `IGitClonerClient`, and `IChunkingService` (each class now `implements` its interface) specifically to make this testable, then wrote the first test suite this service has ever had — which immediately caught two real bugs in the tests themselves before they could ship: a fake `EnrichedChunk` missing a required field the type system caught correctly, and a shared logger spy not being reset between tests, causing later tests to silently find log entries left over from earlier ones — exactly the kind of test-isolation bug that produces confusing, flaky-looking failures if not caught by actually running the suite rather than just reading it.
- [x] **Task 2 — Chat/retrieval observability.** `RetrievalService` now logs a `"Retrieval complete"` summary with chunk count, the highest similarity score among retrieved chunks, and a query-embedding vs. vector-search timing breakdown — the latter split deliberately, since one is CPU-bound local inference and the other a real database round-trip, meaning slow retrieval points to a different fix depending on which one is actually slow. `GroqChatClient` now logs an `"LLM response complete"` line with time-to-first-token (a genuinely different, useful number from total duration for a streaming UX — a slow total time with a fast first token still *feels* responsive) and token usage, all self-contained inside the client so `IChatCompletionProvider`'s interface — and everything downstream of it, including the SSE route — needed zero changes. Finding the correct token-usage field required real investigation: an initial guess (`chunk.usage`) failed a type-check immediately, and checking `groq-sdk`'s actual type definitions showed the real path is `chunk.x_groq.usage`, nested under Groq-specific metadata rather than a top-level field the way it might be on an OpenAI-compatible API — a genuine correction, not assumed correct from a plausible-looking guess. `ChatOrchestrationService` ties both together with one `"Chat response complete"` summary per chat turn, matching the same "individual stage logs plus one summary" pattern established for the import pipeline in Task 1. Tests specifically targeted a real class of bug: verifying `topScore` reflects the actual maximum among multiple different scores (not accidentally the first or last result), and that `topScore` is `null` — not `-Infinity`, what `Math.max()` silently returns on an empty array — when no chunks are retrieved at all.

## Milestone 1.5 — Production Hardening (complete)

A full production-readiness audit was performed after Milestone 1 (`docs/production-readiness-audit.md`) — it's worth reading in full, since it's an honest account of real gaps found by checking the code, not a generic checklist. Hardening work proceeds one task at a time, each with its own rationale, self-review, and tests, tracked below:

- [x] **Task 1 — Secure logging.** The audit found `Authorization` headers were logged in plaintext on every authenticated request (verified directly in this project's own dev logs). Fixed via `pino`'s `redact` option (`src/utils/logger.ts`), covering the specific leak (`req.headers.authorization`, `req.headers.cookie`) plus defense-in-depth wildcard coverage for any field named `password`, `passwordHash`, `accessToken`, `refreshToken`, or `token` appearing anywhere in a logged object — not just the one path that happened to be noticed. Verified both manually (a standalone script proving redaction actually fires) and with an automated test suite (`tests/logger-redaction.test.ts`) that imports the exact same redaction list the real logger uses, so the test can't silently drift from what's actually configured.
- [x] **Task 2 — Rate limiting.** The audit found zero rate limiting anywhere. Fixed with `express-rate-limit`, applied two ways: **IP-based** on `/api/auth/register` and `/api/auth/login`, sharing one combined budget of 5 total attempts/15 min per IP (a deliberate choice — a separate budget per endpoint would let an attacker interleave register and login attempts to double their effective rate) and **user-based** (keyed by `req.userId`, applied *after* `requireAuth`) on `POST /api/repositories` (10/hour — the most expensive operation this API performs: a real clone plus CPU-bound local embedding) and `POST /api/chats/:id/messages` (30/hour — real but cheaper than a full import). All three report through the app's standard `{ error: { code, message } }` shape via the existing `RateLimitedError` class, which the earlier audit had flagged as unused dead code — it's live now. A genuine additional finding surfaced while implementing this: `app.set('trust proxy', ...)` was never configured, which would have made IP-based limiting silently useless the moment this deploys behind Render's reverse proxy (every request would appear to share the proxy's IP) — fixed alongside this task. Verified with real runtime tests (not just type-checking) proving the Nth request actually gets blocked, that per-key counters are genuinely independent, and that a second bug — the default in-memory store's low test-appropriate limits would have broken the existing `auth.routes.test.ts` suite, which legitimately registers several users in sequence — was caught and fixed before it could ship broken. Also verified live: manual testing initially looked confusing (the limiter triggered on the 4th wrong-password attempt, not the 6th) until realizing the earlier account-setup calls (a login, then a register) had already consumed 2 of the 5 shared slots — confirmed as correct behavior for the shared-budget design, not a bug, and the code comment was tightened to make this explicit for the next reader. A third bug surfaced only once the server was actually started locally (not caught by automated tests, since it fires at module-load time rather than per-request): `express-rate-limit`'s startup validation rejected the user-scoped limiters' `keyGenerator` (`ERR_ERL_KEY_GEN_IPV6`) because their defensive fallback to `req.ip` — for a case that should never actually happen, since these limiters only run after `requireAuth` — used the raw IP directly instead of the library's own `ipKeyGenerator()` helper, which normalizes IPv6 addresses to a subnet prefix so a client can't bypass the limit by rotating through addresses in the same subnet. Fixed by wrapping the fallback in `ipKeyGenerator()`; verified by directly constructing the Express app in isolation to prove the validation error was actually gone, not just assumed fixed, then confirming the full test suite still passed.
- [x] **Task 3 — Refresh token flow.** The audit found `register`/`login` issued a refresh token that no endpoint could ever redeem. Recommendation (implement, not remove): a genuinely unusable 15-minute session was the actual alternative, and every other "found but unused" gap in this audit got fixed rather than deleted. Implemented as **rotation with reuse detection** — each refresh token carries a unique `jti` tracked in a new `refresh_tokens` collection (a plain JWT alone can't be individually revoked or single-use; the `jti` is what adds that). Every successful `POST /api/auth/refresh` burns the presented token and issues a brand new pair; presenting an already-rotated-out token a second time is treated as the specific signal of theft and revokes *every* refresh token for that user, not just the reused one — the attacker may already hold a more recent one from the same family. `POST /api/auth/logout` (revoking the presented token) came essentially free once this infrastructure existed and closes another gap the audit named separately, rather than building the same collection twice later. `RefreshTokenModel` uses a MongoDB TTL index so expired records clean themselves up automatically, no cron job required. Two real things self-review caught before shipping: (1) a wrong test assertion — expecting two access tokens minted within the same wall-clock second to always differ, which isn't a real guarantee this system makes (JWT's `iat` only has second-level granularity; the refresh token's `jti`-driven uniqueness is what rotation actually depends on, and that *is* tested and enforced); (2) `ChatModel` and `MessageModel` had been missing from the startup index-readiness wait since Day 5 — the exact class of bug that caused the Day 3-4 chunk-idempotency race — caught and fixed for all three new/existing models while implementing this task, not just the new one.
- [x] **Task 4 — Restrict CORS.** The audit found `cors()` called with no options, defaulting to `Access-Control-Allow-Origin: *` — any website could make cross-origin requests to this API from a browser. Fixed with an `ALLOWED_ORIGINS` env var (comma-separated, defaulting to common local dev frontend ports so local development doesn't regress), passed directly as `cors()`'s `origin` array. Worth being precise about a real limitation of this task: CORS is enforced by the *browser* reading the `Access-Control-Allow-Origin` response header, not by the server refusing to respond — none of this project's usual PowerShell/`Invoke-RestMethod` verification steps can test it, since those tools ignore CORS entirely. Verified instead with a dedicated test suite asserting the actual response headers our configuration produces: an allowed origin gets echoed back in `Access-Control-Allow-Origin`, a disallowed one gets no such header at all (confirmed directly in the `cors` package's real behavior, not assumed from its documentation), and a request with no `Origin` header (a server-to-server call) is unaffected either way.
- [x] **Task 5 — Health/readiness endpoint.** The audit found `/health` returned `{status: "ok"}` unconditionally, never checking whether MongoDB was actually connected — a liveness-only check with no way to detect "the process is up but useless right now." Split into `/health/live` (always 200 if the process can respond at all — deliberately checks nothing else, since restarting a healthy process over a momentary DB blip just adds churn without fixing anything) and `/health/ready` (checks `mongoose.connection.readyState`, returns 503 if not fully connected) — the standard liveness/readiness split every real orchestrator (Kubernetes, Render) expects as two separate probes, not one combined endpoint. Deliberately scoped to MongoDB only, not Groq or the embedding model — Mongo is touched by every request (even a JWT-only auth check hits the DB), while Groq only matters for chat requests and the embedding model has no ongoing "connection" to check the way a database does; checking only what can meaningfully fail is more honest than adding checks that would always just return "ok." Verified with a dedicated test suite that includes deliberately disconnecting the real test database mid-run and confirming `/health/ready` correctly reports `503`, then reconnecting so the rest of the suite isn't affected — not just testing the easy "already connected" path. Self-review caught a real break before it shipped: `cors.test.ts` (from Task 4) still referenced the old `/health` path, which no longer existed after this change — caught by grepping for the old path across the whole repo before considering the task done, not left for the next `npm test` to discover.

**Milestone 1.5 is now complete — all 5 tasks closed, each implemented, self-reviewed, tested, and documented.** 102 tests passing at last full count on the real development machine (including every real-MongoDB suite this sandbox couldn't run). Several real bugs were found and fixed along the way that no amount of planning would have caught up front — a Mongoose index-timing race from Day 3-4 recurring in a new model, a startup-time-only validation error invisible to any HTTP-level test, a wrong test assumption about JWT timestamp granularity, and two documentation-drift breaks caught by grepping the repo rather than assuming a change was isolated. That's the actual production-hardening story: not that the code was written correctly the first time, but that a consistent process (explain, implement, self-review, test, document) kept catching what the first pass missed.

## Deployment

### Docker

The original Day 1 `Dockerfile` was written before this project had any native-compiled dependencies and needed real rework once it had three (`bcrypt`, and `sharp`/`onnxruntime-node` via `@huggingface/transformers`):

- **Base image switched from `node:20-alpine` to `node:20-bookworm-slim`.** Alpine uses musl libc; the prebuilt binaries these native packages ship target glibc. Alpine + native npm dependencies is one of the most common, well-documented sources of "works locally, breaks in Docker" failures in the Node ecosystem — a real risk with three native dependencies now, worth the ~130MB larger image size to avoid.
- **Fixed the install step.** It ran `npm ci --workspace=apps/api`, which scopes which workspace's *scripts* run — correct for the later `npm run build --workspace=apps/api`, but not the right way to install a monorepo's full dependency tree. Now runs unscoped (`npm ci`) at the workspace root.
- **Added a `.dockerignore`** (didn't exist before) — host `node_modules`, `.git`, `.env`, and `dist` were never explicitly excluded from the build context.
- **`libgomp1` added defensively** to the runtime image — `onnxruntime-node` commonly links against GNU's OpenMP runtime for parallelized CPU inference. This couldn't be confirmed as strictly necessary without an actual build test, but the failure mode if it's needed and missing is bad (a clean startup, then a crash the first time someone actually imports a repository) — cheap to include either way.
- **A `HEALTHCHECK` directive**, checking `/health/live` (not `/health/ready`) — deliberately the liveness endpoint here specifically, so a transient MongoDB blip doesn't make Docker's own tooling (`docker ps`, compose's `depends_on: condition: service_healthy`) consider the container unhealthy. This is a genuinely different answer from Render's own `healthCheckPath` in `render.yaml`, which *does* check `/health/ready` — two different tools asking two different questions, not an inconsistency. Uses `node` itself to make the HTTP request, since neither `curl` nor `wget` is installed in this minimal image.

**Honest limit on what's verified here:** Docker itself isn't available in the development sandbox this project was built in, so the actual multi-stage `docker build` was never run end-to-end *during development* — and that gap turned out to matter. **A real bug surfaced on the first actual Render deployment:** the runtime image only copied `apps/api/node_modules` from the builder stage, but this is an npm **workspaces** monorepo — `npm ci` run at the repo root **hoists** most shared dependencies (`express` included) up to the root-level `node_modules`, not into the individual workspace's folder. The deployed container failed immediately with `Error: Cannot find module 'express'`, since almost nothing had actually been copied into it. Fixed by copying the builder stage's entire `/app` directory wholesale, preserving the exact relative structure (`/app/node_modules` alongside `/app/apps/api/`) that Node's own module resolution expects — it searches upward through parent directories for `node_modules`, so running from `/app/apps/api/dist/server.js` correctly finds the hoisted packages the same way it did during the build. The trade-off, accepted deliberately: this also ships `devDependencies` and TypeScript source into the runtime image, a real image-size cost worth trimming later with a proper `npm ci --omit=dev` production-only install stage — but getting an actual, correct, deployed container came first, verified live, before that optimization was worth the risk of a second untested Dockerfile change.

**Running `docker build` (or `docker compose up --build`) yourself locally is still the fastest way to catch a bug like this before it reaches a real deployment** — treat it the same way live testing has caught real bugs automated tests couldn't, throughout this whole project.

### Render

`render.yaml` at the repo root is a [Render Blueprint](https://render.com/docs/blueprint-spec) — connect this repo in the Render Dashboard and choose "Deploy Blueprint," and Render detects and applies it automatically.

A few decisions worth understanding, not just copying:

- **`dockerfilePath: apps/api/Dockerfile` with `dockerContext: .`** (the repo root, not `apps/api/`) — the Dockerfile's own `COPY package.json package-lock.json* ./` step expects the full monorepo root as build context to resolve the npm workspaces dependency tree correctly.
- **`healthCheckPath: /health/ready`, not `/health/live`.** This is the opposite choice from the Docker `HEALTHCHECK` directive above, and deliberately so: Render's own health-check documentation explicitly recommends checking operation-critical dependencies (their own example is "executing a simple database query to confirm connectivity"), and — unlike a bare Kubernetes liveness probe — Render's `healthCheckPath` already has built-in grace periods (15s before pausing traffic to a failing instance, 60s before restarting it) that absorb a momentary Mongo blip on their own. Using `/health/ready` here follows Render's own stated platform design rather than mechanically porting a Kubernetes liveness-only convention onto a platform that isn't Kubernetes.
- **`JWT_SECRET` uses `generateValue: true`** — Render generates a cryptographically random value itself; there's no need to run `openssl rand -base64 32` and paste it in by hand for this one specifically.
- **Every other secret (`MONGODB_URI`, `GROQ_API_KEY`, `ALLOWED_ORIGINS`, `GITHUB_TOKEN`) is marked `sync: false`** — Render creates the environment variable but leaves it empty, prompting you to fill in the real value in the Dashboard after the Blueprint runs. None of these are ever committed to source control, even as placeholders.

After the Blueprint creates the service, go to its Environment tab and fill in the four `sync: false` values before the first deploy will actually work end-to-end.

### Smoke testing a deployment

**A real, confirmed production incident, worth documenting in full:** the first actual deployment to Render's free tier crashed mid-import. The smoke test's polling step failed with a `502 Bad Gateway`; cross-referencing the application logs against Render's own **Events** tab (which records infrastructure-level incidents separately from application output) confirmed the exact cause: `"Instance failed: Ran out of memory (used over 512MB) while running your code"`, timestamped to the second against the log line `"Loading local embedding model"` roughly 35 seconds earlier — the container was OOM-killed while loading the embedding model for the first time, and the in-progress import job was silently and permanently lost, since it had no persistence or recovery mechanism (the exact gap the production audit's #1 finding had already flagged, now observed causing real data loss rather than staying theoretical).

**Root cause:** `LocalEmbeddingClient` loaded the embedding model at full `fp32` precision by default — roughly 4x the memory footprint of an 8-bit quantized version of the same model, comfortably exceeding Render's free-tier 512MB limit once combined with Node's own baseline memory and the rest of the loaded dependency tree.

**Fix, attempt 1 (wrong):** the first fix specified `dtype: 'q8'` (8-bit quantization), reasoning generically that quantization reduces memory. This failed differently on redeploy — a clean `"Could not locate file: model_quantized.onnx"` error instead of an OOM crash, because **this specific model repository doesn't actually publish an int8/q8 variant at all.** Different Hugging Face model repos publish different sets of quantized files; assuming a dtype name without checking the actual repository's file listing was the mistake.

**Fix, attempt 2 (verified against the real file listing, still not enough):** checked `onnx-community/all-MiniLM-L6-v2-ONNX`'s actual files on Hugging Face directly — only `fp32` (default, ~90.3MB), `fp16` (~45.1MB), `q4` (~54.4MB), and `q4f16` (~29.8MB) exist. `dtype: 'q4f16'` was chosen as the smallest available option (roughly 3x smaller than the crashing default). This deployed and ran cleanly for a moment, then crashed with the identical OOM signature three minutes later.

**Fix, attempt 3 (targets the actual mechanism, not just model size):** the redeployed `q4f16` container crashed with the identical OOM signature (exit code `137` — Linux's SIGKILL, confirmed again via Render's Events tab). This showed model file size wasn't the dominant factor after all — `onnxruntime`'s own defaults (a pre-reserved CPU memory arena, per-thread buffers) allocate meaningful memory independent of model size, tuned for a normal multi-core machine rather than a fractional-CPU container. `session_options` now explicitly disables the memory arena and memory-pattern optimization and caps thread counts to 1 each — standard, documented levers specifically for memory-constrained deployments, verified against the real `onnxruntime-common` type definitions rather than guessed. **One correction to the earlier version of this account, checked directly against Render's current pricing before writing it down**: Render's Starter plan ($7/month) has the *identical* 512MB RAM as the free tier — it only removes the sleep/spin-down and adds more CPU. Real additional RAM only starts at Standard ($25/month, 2GB).

**This third fix still crashed identically on the 40-file `klona` test repo — the actual resolution turned out to be different from all three attempts above.** A diagnostic test against a genuinely tiny repository (`sindresorhus/is-fullwidth-code-point`, ~4-5 files) passed cleanly end to end, proving the crash was **repo-size-dependent**, not a fixed baseline problem the way all three code-level attempts assumed. The real, working, entirely free fix required no code change at all: **`MAX_REPO_FILES`** — already a configurable environment variable, previously left at a generous default of `3000` that assumed far more memory headroom than this specific 512MB deployment actually has — was lowered to `15` directly in Render's dashboard. This doesn't work around the memory ceiling; it makes the *existing* safety check (already present in `repo-file-walker.ts`, designed for exactly this purpose) actually reject an oversized repository cleanly, with a proper validation error, before the memory-intensive embedding step ever starts — confirmed live: importing `klona` (40 files) now fails immediately with a clean validation error instead of crashing the whole container.

**The real lesson from this whole saga, worth sitting with rather than glossing over:** three plausible, well-reasoned, individually-verified-against-real-documentation code fixes (smaller model, smallest available quantization, constrained runtime memory settings) all failed to fix the actual problem, because none of them addressed the actual variable that mattered — the size of the data being processed, not the size of the model processing it. The fix that worked was found only by testing a hypothesis directly (does this scale with repo size?) rather than continuing to refine the same category of fix. Live testing here didn't just catch a bug faster than reasoning about it alone would have — it corrected the entire direction of the investigation.

**This third fix has, once again, not yet been verified against a real redeploy.** Three fix attempts in a row needing an actual live test to confirm or disprove each one is itself worth sitting with, not glossing past: a plausible, well-reasoned explanation is not the same thing as a confirmed one, no matter how many times it's tempting to treat it that way.

**If quantization alone isn't enough:** the next fallback, in order of preference, is upgrading Render's plan (more RAM, no code change, but a real ongoing cost) — not re-architecting the import pipeline, since the actual bug here was a specific, fixable memory-precision choice, not a fundamentally unfixable design flaw.

`scripts/smoke-test.ps1` exercises the exact same flow verified manually throughout local development — health checks, register, import a real repo, poll until ready, start a chat, ask a real question — against a live deployed URL, so deployment verification is a repeatable script rather than a one-time manual check nobody runs again after the first deploy:

```powershell
.\scripts\smoke-test.ps1 -BaseUrl "https://your-service.onrender.com"
```

**Honest limit on what's verified here:** this script was written and self-reviewed against exactly the request/response shapes this project has empirically confirmed, repeatedly, throughout local development (including the specific, previously-surprising observation that `Invoke-RestMethod` returns an SSE chat response as raw text containing literal `"token"` and `event: done`/`event: error` substrings) — but it has never been executed against a real deployment, since that requires an actual Render account and deployed service neither exists in the development sandbox this project was built in. **Running it yourself against your real deployed URL is the genuine verification step.**
